## G2


### A

```markdown
## 變更內容

`lib/api/client.js` 的 `request()` 加入重試：狀態碼落在 502、503、504 時重試，最多 3 次請求（初次加 2 次重試），間隔採指數退避 200ms、400ms。其他狀態碼與第 3 次失敗維持原行為，直接丟出 `ApiError`。逾時設定 `TIMEOUT` 8000ms 不變，套用在每一次請求上，因此最壞情況總耗時約 24.6 秒。

## 驗證方式

1. 用 mock server 讓某個 endpoint 回 503，確認 client 送出 3 次請求、間隔約 200ms 與 400ms，最後丟出 `ApiError(503)`。
2. 同一個 endpoint 改回 400，確認只送出 1 次請求就丟出 `ApiError(400)`。
3. 讓第 2 次請求回 200，確認 `request()` 正常回傳 JSON，不再繼續重試。

## 需要一併確認

非 idempotent 的請求（POST 建單、付款）走到 502/503/504 時會重送，若後端未做冪等處理有重複建立的風險。目前 `request()` 不分 method 一律重試，審查時請確認呼叫端是否有這類情境。
```


### B

```markdown
## 摘要

`request()` 遇到 502、503、504 時自動重試，最多兩次；其餘狀態碼與原本一樣直接丟出 `ApiError`。
重試間隔為指數退避 200ms、400ms，單次請求的 8 秒 timeout 不變，因此最壞情況的總耗時從 8 秒變成約 24.6 秒。

## 變更內容

- 新增 `RETRYABLE` 狀態碼集合（502 / 503 / 504）。
- `request()` 改為最多三次嘗試的迴圈；成功即回傳，不可重試或次數用盡即丟出 `ApiError`。

## 驗證方式

1. 用 mock server 讓 `/foo` 連續回 503 兩次、第三次回 200，確認 `request('/foo')` 回傳資料，且 fetch 被呼叫三次。
2. 讓 `/foo` 固定回 503，確認第三次之後丟出 `ApiError(503)`，總共呼叫三次。
3. 讓 `/foo` 回 400，確認立即丟出 `ApiError(400)`，只呼叫一次。

## 審查重點

- 重試會重送同一份 `options`，若 `body` 是 stream 或 `FormData` 有消耗性內容，第二次送出會是空的。目前呼叫端是否只傳 plain object？
- 非冪等的請求（POST 建立訂單）如果後端已收到但回 502，重試會造成重複建立。若有這類端點，需要額外的冪等鍵或改為只對 GET 重試。
```


### C

```
## 變更內容

`request()` 對 502／503／504 加入重試，最多重試 2 次（共 3 次請求），退避間隔 200ms、400ms。
其他狀態碼與逾時維持原本行為：直接拋出 `ApiError`。

## 驗證方式

1. 讓後端（或 mock）回 503，觀察 network 面板應看到 3 次請求，間隔約 200ms 與 400ms，最後拋出 `ApiError(503)`。
2. 讓後端回 400 或 500，應只送出 1 次請求並立即拋錯。
3. 正常回應維持單次請求。

## 注意事項

重試不分辨請求方法，非等冪的 POST 若在後端已處理成功但回 502，會被重送。
目前後端 502/503/504 多發生在未進入應用層時，風險可接受；若之後有非等冪端點需排除，需再加白名單。
```

## G3


### A

## `experimental.dedupeRequestsPerRender`

開啟後，同一次 render 期間內容相同的查詢只會實際送出一次請求，其餘呼叫共用同一個結果。暫存區是 request 層級的，render 結束就整份丟棄，因此不會跨請求或跨使用者共用資料。適合用在多個元件各自取用同一份資料的頁面，可省下重複往返；若你的元件刻意要在同一次 render 內重新取得最新資料，就不該依賴這個選項。此為 experimental 選項，升版 Next.js 時需一併確認行為是否變動。


### B

```markdown
### `experimental.dedupeRequestsPerRender`

開啟後，同一份查詢在單次 render 內只會送出一次請求，結果放在 request 層級的暫存區，render 結束就丟掉。用途是避免多個元件各自取同一份資料時重複打 API，不需要改寫元件把資料提到上層再往下傳。

因為暫存區的生命週期只有一次 render，跨請求不會拿到舊資料，也不能當快取用。目前仍在 `experimental`，升級 Next.js 版本時要重新確認行為。
```


### C

`dedupeRequestsPerRender` 開啟後，同一次 render 內重複的查詢只會實際送出一次，其餘取用同一份結果；暫存區綁在單次 request 上，render 結束就丟棄，不會跨請求共用資料。用途是省掉在元件樹裡到處傳 props 或自建 context 的工夫，同一份資料在多個元件各自取用即可。判斷是否重複依查詢的識別條件（路徑與參數）而定，因此帶有時間戳或隨機值的參數會被視為不同查詢，不會合併。這是 `experimental` 選項，升級 Next.js 時要一併確認行為是否改變。
