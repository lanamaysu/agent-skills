## G2

```markdown
## 摘要

`request()` 遇到 502、503、504 時自動重試，最多兩次；其餘狀態碼與原本一樣直接丟出 `ApiError`。
重試間隔為指數退避 200ms、400ms，單次請求的 8 秒 timeout 不變，因此最壞情況的總耗時從 8 秒變成約 24.6 秒。

## 變更內容

- 新增 `RETRYABLE` 狀態碼集合（502 / 503 / 504）。
- `request()` 改為最多三次嘗試的迴圈；成功即回傳，不可重試或次數用盡即丟出 `ApiError`。

## 驗證方式

1. 用 mock server 讓 `/foo` 連續回 503 兩次、第三次回 200，確認 `request('/foo')` 回傳資料，且 fetch 被呼叫三次。
2. 讓 `/foo` 固定回 503，確認第三次之後丟出 `ApiError(503)`，總共呼叫三次。
3. 讓 `/foo` 回 400，確認立即丟出 `ApiError(400)`，只呼叫一次。

## 審查重點

- 重試會重送同一份 `options`，若 `body` 是 stream 或 `FormData` 有消耗性內容，第二次送出會是空的。目前呼叫端是否只傳 plain object？
- 非冪等的請求（POST 建立訂單）如果後端已收到但回 502，重試會造成重複建立。若有這類端點，需要額外的冪等鍵或改為只對 GET 重試。
```

## G3

`dedupeRequestsPerRender` 開啟後，同一次 render 內重複的查詢只會實際送出一次，其餘取用同一份結果；暫存區綁在單次 request 上，render 結束就丟棄，不會跨請求共用資料。用途是省掉在元件樹裡到處傳 props 或自建 context 的工夫，同一份資料在多個元件各自取用即可。判斷是否重複依查詢的識別條件（路徑與參數）而定，因此帶有時間戳或隨機值的參數會被視為不同查詢，不會合併。這是 `experimental` 選項，升級 Next.js 時要一併確認行為是否改變。
